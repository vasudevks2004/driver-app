# Low-cost OTP setup

## Use the app now without SMS charges

Use the explicit **debug-only** entry point:

```powershell
flutter pub get
flutter run -t lib/main_dev.dart
```

Choose the Android device/emulator. No `config/auth.json` or Supabase credentials are required.

- Country code: **+91**
- Test mobile: **9876543210**
- Test OTP: **123456**

Use **Send OTP**, then enter the test code. The same number/code works for **Register as a new driver**. Enter sample name/city, confirm the review acknowledgement, then verify and try the licence/selfie steps. The registration receipt explicitly says it is a local preview. After signing out, test phone login opens the actual dashboard using local sample data.

The yellow banner stays visible on every screen. Nothing is sent to SMS, Auth, the driver API, private Storage, or DigiLocker. Photos/applications are held in memory and disappear when the app restarts. Existing production secure sessions are not loaded or overwritten. Even inherited HTTP methods have a transport that refuses network access. Google and email actions show a preview-specific message instead of opening live accounts.

This simulates the user flow; it does not verify ownership of a real mobile number. The preview is refused outside debug builds and is never imported by production `lib/main.dart`. Production builds cannot accept this fixed test OTP through the preview code.

## Live Indian SMS through MSG91

The Supabase SMS hook is in `supabase/functions/send-sms-msg91`. It uses MSG91's **transactional Flow SMS API**, with the OTP generated by Supabase inserted into an approved template variable. The mobile app continues calling Supabase's `/otp` and `/verify` endpoints. It does not verify codes using MSG91 or grant roles based on delivery results.

Live delivery still requires an MSG91 account, an active auth key, credits, and an approved India SMS template/sender setup. Complete any DLT/registration requirements shown by MSG91 for your route. Choose the transactional SMS/Flow template, not an OTP Widget that generates a different code. Confirm the provider's current route, pack, tax and onboarding charges before adding funds. No plan, number or SMS pack has been purchased by this change.

Official references:

- [MSG91 transactional SMS](https://msg91.com/in/sms)
- [MSG91 SMS API](https://docs.msg91.com/sms/send-sms)
- [Supabase Send SMS Hook](https://supabase.com/docs/guides/auth/auth-hooks/send-sms-hook)
- [Supabase hook plans and time limits](https://supabase.com/docs/guides/auth/auth-hooks)

### Server configuration

1. Apply `supabase/setup-sms-receipts.sql` to the same Supabase project. It adds a service-only delivery receipt table with RLS and no direct client access. Rows hold hashes/status only, never phone numbers or codes.
2. Deploy `send-sms-msg91` with JWT gateway validation disabled. The function authenticates **Standard Webhooks signatures** before any paid provider request. Never expose an unsigned forwarding endpoint.
3. Configure an **HTTP Send SMS** Auth Hook pointing to:

   `https://rzynmkewypubveiqneat.supabase.co/functions/v1/send-sms-msg91`

4. Generate the hook signing secret in Supabase. Save the following secrets under **Edge Functions → Secrets**, directly in the dashboard:

   | Secret | Value |
   | --- | --- |
   | `SEND_SMS_HOOK_SECRET` | Exact generated signing secret, including `v1,whsec_` if shown |
   | `MSG91_AUTH_KEY` | Your MSG91 key; never add it to Dart or Git |
   | `MSG91_TEMPLATE_ID` | Approved MSG91 transactional Flow template ID |
   | `MSG91_OTP_VARIABLE` | Exact template variable name, such as `VAR1`; case matters |
   | `MSG91_SMS_ENABLED` | `true` only after the remaining setup is complete |

   Supabase supplies `SUPABASE_URL` and `SUPABASE_SERVICE_ROLE_KEY` server-side. Never copy those secrets into the app.

5. Enable the HTTP Send SMS hook, then enable Phone sign-in. Keep phone confirmations enabled, OTP length **6**, expiry **300 seconds**, and resend interval at least **60 seconds**. Retain Auth rate limits. The hook replaces the Twilio sender; Twilio credentials are not needed for an active custom hook. If the dashboard still demands Twilio fields while a hook is enabled, stop and inspect the displayed validation rather than entering fake credentials.
6. Run the production entry point and test with the account owner's real mobile number:

   ```powershell
   flutter run -t lib/main.dart --dart-define-from-file=config/auth.json
   ```

7. Verify SMS arrival, correct/wrong/expired codes and resend. Confirm new applicants reach registration, while existing approved drivers still require trusted `/drivers/me` membership checks.

Live activation cannot be completed without the real MSG91 key/template and Supabase hook secret. Missing secrets or an inactive flag return an error; the function never silently accepts delivery.

### Delivery protections

The function accepts Indian mobile numbers and six-digit codes only. Signatures bind request ID, timestamp and original body; timestamps outside five minutes, forged/tampered requests, malformed bodies and oversize payloads are rejected. Secrets, codes and phone numbers are not logged or included in URLs. Provider redirects are refused.

A unique persistent request hash reserves delivery before sending. Duplicate callbacks return success only when the existing receipt is marked sent; ambiguous/failed attempts do not trigger another paid SMS under the same callback ID. A fresh OTP request after the normal cooldown gets a new callback ID. The entire HTTP flow has a 4.5-second deadline to fit Supabase's five-second hook limit.

A successful provider response means **accepted for sending**, not handset delivery. Check MSG91 delivery reports for actual delivery. Periodically delete receipt rows older than seven days using an authorized maintenance job; this is longer than the accepted signature window. No actual user records or OTPs are stored in this table.
